# Android 安装包删除与标题统一设计

日期：2026-08-09

## 背景

安装包页面当前通过 `FileManager.listPatchedApks()` 展示应用生成的补丁 APK。每个条目只有“保存到下载”操作，页面标题仍显示“我的补丁”。用户需要对每个安装包独立删除，并将标题统一为“安装包”。

## 目标

- 每个安装包条目提供独立的删除按钮。
- 删除前明确提示将删除的应用生成补丁 APK。
- 删除成功后列表立即反映结果，失败时显示可重试错误。
- 删除动作不卸载手机中的游戏，不删除用户原始 APK。
- 仅删除应用专用 `SLG-Translator-Output` 目录中的匹配 `*-patched-signed.apk`。
- 不复用或扩大现有 `cleanupStorage` 的清理范围。
- 页面可见标题和无障碍标签统一使用“安装包”。

## 方案

采用原生精确删除接口配合前端确认交互：

1. `InstallSupport` 增加 `deletePatchedApk`，并收紧 `listPatchedApks` 只扫描应用专用的 `SLG-Translator-Output` 目录，不再扫描其父目录或应用 files 根目录。
2. 原生接口只接受列表返回的绝对 `file` 路径。删除前解析 canonical path，确认目标是普通文件、文件名以 `-patched-signed.apk` 结尾、没有符号链接，并且严格位于某个专用输出目录之内；路径不存在、目录、兄弟目录、`..` 越界和 `content://` 均拒绝。
3. 删除接口不使用 `resolvePatchFile` 的“找最新文件”兜底。删除前再次执行路径、后缀和文件状态校验，尽量缩小检查与删除之间的竞态窗口。
4. 在 `build_fast_scanner.py` 和现有 FileManager bridge 中加入删除方法的签名、委托和幂等注入，并增加重复注入检查，确保最终 APK 真正暴露该接口。
5. 前端在每个条目右侧加入至少 48dp 触控目标的垃圾桶图标按钮，设置 `aria-label` 和 `title` 为“删除安装包”，并通过 `aria-live`/`aria-busy` 反馈状态。点击后显示确认框，确认文案说明不会卸载游戏或删除原始 APK。
6. 前端按路径维护删除中的集合，阻止同一条目重复请求；删除成功后重新读取列表，刷新失败时保留旧列表并提供重试；删除行消失后把焦点移到相邻条目或页面标题。
7. 右上角页面标题、页面 `aria-label` 和相关空状态文案从“我的补丁”改为“安装包”。

现有 `cleanupStorage` 继续保持独立语义，不作为安装包列表的删除实现，也不由本次按钮触发。它的宽泛清理行为必须在单独入口和单独确认文案中表达。

## 缓存边界

当前翻译缓存是跨任务共享的，没有按安装包建立独立索引。删除按钮只清理专用输出目录中的对应补丁 APK，不删除无法证明属于该安装包的共享翻译缓存，以免破坏翻译续作和历史记录。这里的安全承诺是“删除应用输出目录中的匹配 APK”，不把文件名后缀单独当作完整 provenance 证明。

## 失败处理

- 路径为空、文件不存在、路径不在应用输出目录、文件名后缀不匹配时，原生接口拒绝删除并返回明确错误。
- 路径为 `content://`、相对路径、符号链接、目录或位于兄弟目录/输出目录外时，原生接口拒绝删除并返回明确错误。
- 删除过程中列表保持可用，同一路径按钮进入禁用状态，防止重复请求。
- 原生删除成功但刷新失败时，保留旧列表并显示可重试的刷新错误；下次进入页面仍可重新读取真实文件状态。
- 确认取消不调用原生接口；删除失败后恢复按钮、保留条目并将焦点落回该条目。

## 验证

- Python 合约测试验证标题、删除按钮、确认取消、重复点击保护、成功刷新、刷新失败保留旧列表、焦点转移和无障碍状态。
- Java/原生合约测试验证专用目录范围、canonical containment、后缀、目录、缺失文件、`..`、兄弟目录、符号链接和拒绝危险路径。
- bridge 构建测试验证 `deletePatchedApk` 的签名、委托、幂等注入和最终 APK 方法存在性。
- 构建 APK、签名、安装到真实设备。
- 在设备上记录每个 APK 的绝对路径、SHA-256 和大小，验证多个安装包逐个删除、取消删除不改变列表、删除后 APK 不再出现、删除失败可重试、原始 APK 哈希不变、已安装游戏仍可启动，并确认最终安装 APK 的 SHA-256 与本次构建一致。
- 在设备上使用 TalkBack/无障碍树确认删除按钮有可读名称、触控目标足够大、状态变化可被播报。
