# Ren'Py 批次 B/C 完整重验与发布收口设计

## 1. 背景

本设计承接 `docs/superpowers/plans/2026-08-07-renpy-app-compatibility-optimization.md`。原计划 Task 0–15 已有实现提交，Task 16 也已建立兼容性矩阵、发布检查清单和若干机器断言，但现有证据不足以证明整个计划完成。

2026-08-07 的最新完整测试基线为：

```text
python -m unittest discover -s . -p "test_*.py" -v

Ran 167 tests in 181.052s
FAILED (failures=25, errors=1, skipped=1)
```

25 个失败和 1 个错误集中在 `apk-work/ui-redesign/test_workshop_patch.py`。此外，Task 15 缺少真实游戏的新游戏、旧存档、rollback、跳转和语言切换证据；Task 16 缺少真实第三方 Ren'Py 游戏和真实 Android 设备上的完整端到端证据。因此，已有提交只能作为候选实现，不能自动等同于验收通过。

## 2. 目标

建立一条不可跳步、可复现、可审计的完整重验链路：先使 `test_workshop_patch.py` 与当前权威产品行为一致，再从 Task 6 开始逐项重验批次 B 和批次 C，最后执行 Task 16 的机器测试、APK 构建、真实游戏和真机发布门禁。

完成后的产品和证据必须能够回答：

- 提取了哪些 Ren'Py 文本，遗漏或不确定的是哪些；
- 哪些译文通过或未通过确定性校验；
- 为什么允许或禁止构建；
- 目标字体是否覆盖译文使用的全部字符；
- 目标引擎、RPYC、RPA、语言激活和 APK 安装形态属于哪个兼容等级；
- 生成的 RPYC、APK、签名和安装结果是否经过独立验证；
- 新游戏、旧存档、rollback、跳转和语言切换是否在真实设备上成立；
- 发布状态为什么是“批准”“未批准”或“等待外部验收”。

## 3. 非目标

- 不重新设计应用主流程或视觉风格。
- 不移植完整 Ren'Py Python 解释器或编译器。
- 不扩大原计划支持范围，不把未知 AST、pickle 或 RPA 结构猜测为可写。
- 不把 fixture、静态字符串断言、APK 成功生成或安装成功替代真实游戏运行证据。
- 不为了获得绿色测试而删除安全门禁、放宽失败条件或复制乱码断言。
- 不清理工作区中的无关未跟踪文件，不改写用户已有暂存内容。

## 4. 核心原则

### 4.1 当前证据优先

每个原任务都重新建立“原文要求 → 当前实现 → 自动化证据 → 外部证据 → 缺口”的映射。历史提交、进度台账和先前测试只用于定位，不作为当前完成证明。

### 4.2 不通过当前门禁，不进入下一阶段

阶段顺序固定为：

```text
Phase 0  冻结重验基线
  ↓
Phase 1  完全对齐 test_workshop_patch.py
  ↓
Phase 2  完整重验批次 B（Task 6–12）
  ↓
Phase 3  独立重验批次 C（Task 13、14、15）
  ↓
Phase 4  执行 Task 16 发布级验证
  ↓
Phase 5  完成审计与发布批准
```

如果某阶段失败，只能在该阶段内继续调查、修复和验证；不能以专项测试通过为由跳过全量回归。

### 4.3 测试和产品都可能出错

`test_workshop_patch.py` 的失败不能预先全部归为“旧测试”，也不能预先全部归为“产品回归”。每个失败必须先找到根因和权威行为来源，再决定修改测试、产品实现或测试夹具。

### 4.4 缺少证据不等于通过

所有要求只允许三种结果：

- `PASS`：存在直接、当前、可重复的证据；
- `FAIL`：证据与要求冲突；
- `NOT-RUN`：缺少真实样本、设备或其他外部条件。

不得使用“应该可用”“已有代码”“理论兼容”“未发现问题”替代 `PASS`。

## 5. 阶段设计

### 5.1 Phase 0：冻结重验基线

Phase 0 建立后续所有结论的统一起点：

- 固定源 APK 的 GitHub 仓库、commit、文件路径和 SHA-256；
- 记录当前分支、HEAD、Python、Java、Node、Android SDK/build-tools 版本；
- 运行并保存完整 discover 的测试总数、失败、错误和跳过项；
- 保存所有失败测试名称及其首个有效异常，不把超长压缩 JavaScript dump 当作根因；
- 记录 `git status --short --branch`，区分用户暂存文件、任务文件和无关未跟踪文件；
- 创建独立的完整重验进度台账和证据目录约定。

Phase 0 只读采集证据；此处“只读”指不修改产品逻辑和既有行为测试。
允许 Task 0 新增一个不改变产品行为的 evidence schema machine assertion，
用于校验固定九列表格、任务行集合和显式状态；不得借此修改原始产品行为。

### 5.2 Phase 1：完全对齐 `test_workshop_patch.py`

每个失败进入统一根因记录：

```text
测试名称
稳定复现命令
首个有效失败
测试期望
当前实现行为
权威产品行为来源
根因分类
应修改的文件
红灯证据
绿灯证据
相关回归结果
```

根因分类固定为：

1. 产品实现回归；
2. 测试仍断言旧行为；
3. 测试依赖压缩 JavaScript 的脆弱内部结构；
4. 产品、生成资产或测试存在编码边界错误；
5. 测试夹具没有模拟当前 React/Capacitor 状态；
6. 外部条件缺失。

失败按职责分组处理：

- 完成页、空扫描和恢复状态；
- 已安装应用选择、请求 epoch 和共享 APK loader；
- 网络错误、批次终止和禁止产出部分补丁；
- 翻译缓存、模型切换和缓存命名空间；
- 进度日志、长任务状态和可见工作台；
- 设置页、供应商、模型和自定义 endpoint；
- 存档导入、导出和游戏选择；
- RPYC 字符串过滤、换行和编码；
- Android shell、底部导航和安装动作。

测试修改规则：

- 当前产品违反已批准的新行为或安全门禁时，修改产品实现；
- 产品符合当前规格而测试仍断言旧行为时，修改测试；
- 测试通过搜索压缩 bundle 内部位置来推断行为时，改为稳定语义断言或可执行行为契约；
- 乱码必须追踪到编码边界，禁止复制乱码到新断言；
- 夹具缺少当前状态时，补齐夹具而不是放宽断言；
- 证据不足时保持失败并继续调查。

Phase 1 的完成门禁是 `python -m unittest test_workshop_patch.py -v` 零失败、零错误，并且完整 discover 没有因本阶段产生新的失败。

### 5.3 Phase 2：完整重验批次 B

按原顺序重新验收 Task 6–12：

- Task 6：结构化 Ren'Py 文本记录；
- Task 7：官方标记字符串覆盖；
- Task 8：语境碰撞和结构化翻译语料；
- Task 9：占位符、Ren'Py 标签、插值和 printf lint；
- Task 10：覆盖率、公共文本分类、增量缓存和构建门禁；
- Task 11：中文字体覆盖和东亚断行；
- Task 12：统一兼容性预检报告和 UI。

每个任务先审计已有接口和证据。证据直接覆盖原要求时保留实现并重新运行测试；证据缺失或间接时新增失败测试；证据证明实现有误时进行最小修复。每个任务必须拥有独立的专项回归、`test_workshop_patch.py` 回归和完整 discover 结果。

批次 B 的完成定义是产品能准确解释“翻译了什么、漏了什么、哪些条目被拒绝、为什么允许或禁止构建”，并且这些结论来自结构化数据和确定性门禁，而不是 UI 文案推断。

### 5.4 Phase 3：独立重验批次 C

Task 13、14、15 是三个独立高风险发布单元：

- Task 13：Python 2 / protocol 2 受限 writer；
- Task 14：Split APK 完整扫描、统一签名和单 session 安装；
- Task 15：高级 dialogue ID 翻译模式。

三项必须分别拥有失败测试、修复、专项回归、APK/DEX 证据和独立提交。不得把三项合并为一个未经中间门禁验证的版本。

Task 15 的高级模式保持默认关闭，直到至少一个真实测试游戏证明：

- 新游戏能够显示正确译文；
- 旧存档能够加载；
- rollback 后文本和状态正确；
- jump/跳转后上下文正确；
- selectable language 可切换到译文和切回原文；
- always-on 完成页文案与实际行为一致。

未获得这些证据时，全局 string map 仍为默认路径，不能因为 dialogue fixture 通过而自动启用高级模式。

### 5.5 Phase 4：Task 16 发布级验证

Task 16 分为三个互不替代的证据层：

1. 机器测试：单元、契约、scanner、quality、coverage、performance、完整 discover；
2. 构建验证：helper DEX、APK 资产、zipalign、V2/V3 签名、版本和类归属；
3. 真实运行：真实游戏扫描、翻译、构建、安装、启动、语言激活、字体、旧存档和 rollback。

真实设备链路固定为：

```text
扫描
→ 兼容性预检
→ 覆盖率统计
→ 翻译
→ lint
→ 编译
→ RPYC validator
→ APK 合并
→ 签名
→ 安装
→ 启动
→ 看到译文
→ 加载旧存档
→ rollback
→ 切换语言或确认 always-on 行为
```

单 APK、base + split、selectable 和 always-on 必须分别记录适用样本和结果。`EXTRACT_ONLY` 或 `UNSUPPORTED` 被正确阻断是安全门禁通过，不是该样本可发布的证明。

### 5.6 Phase 5：完成审计与发布批准

最终按原计划逐条核对 Task 6–16 的每个 Step、接口、命令、产物和完成条件。兼容性矩阵、发布检查清单、进度台账和实际命令输出必须一致。

如果任何强制项为 `FAIL` 或 `NOT-RUN`，总体状态保持“未批准”或“等待外部验收”。只有全部强制项为 `PASS`，允许的 skip 都有外部条件说明，且没有未解释失败时，才能批准发布并标记完整重验结束。

## 6. 证据模型

每项要求使用统一证据记录：

| 字段 | 说明 |
|---|---|
| `requirementId` | 稳定标识，例如 `B10-COVERAGE-01` |
| `sourceRequirement` | 原计划中的精确要求 |
| `implementation` | 权威类、函数、bridge 或 UI 状态 |
| `automatedTest` | 直接证明该要求的测试名称 |
| `command` | 可重复执行的精确命令 |
| `status` | `PASS`、`FAIL` 或 `NOT-RUN` |
| `artifact` | 报告、JSON、DEX、APK、签名结果、截图或设备日志 |
| `residualRisk` | 自动化或样本未覆盖的风险 |
| `commit` | 实现或验证该要求的独立提交 |

静态字符串存在性只证明接线存在。运行时状态、失败路径、并发、恢复和安装行为必须使用可执行契约、真实构建或设备证据证明。

## 7. 测试层级

每项修复遵循红—绿流程：稳定复现失败、确认根因、建立或收紧失败测试、实施单一最小修复、运行单测试、运行职责组、运行文件级回归、运行相关专项回归、运行完整 discover。

测试层级固定为：

```text
L1  单元或单契约测试
L2  任务专项测试文件
L3  test_workshop_patch.py
L4  完整 unittest discover
L5  helper DEX 构建与类检查
L6  APK 构建、资产一致性、zipalign 和签名
L7  真实游戏静态审计
L8  真机端到端验证
```

低层通过不能替代高层门禁。某个测试只有在确认其断言直接覆盖对应要求后才能作为完成证据。

## 8. 外部条件与跳过规则

- 没有真实完整 Ren'Py APK 和对应提取语料时，coverage audit 可以显式 skip，但不能声明 `missing == 0`。
- 没有 Android 设备时，安装、启动、语言激活、字体显示、旧存档和 rollback 保持 `NOT-RUN`，发布保持未批准。
- 没有真实 split 应用时，fixture 只能证明 APK 集合机器契约，不能证明 split 真机链路。
- 高级 dialogue ID 模式缺少 rollback 证据时必须默认关闭。
- 外部条件缺失不阻止继续完成本地实现和自动化工作，但阻止最终发布批准。

每个 skip 必须在兼容性矩阵和发布清单中记录缺少的条件、恢复后运行的命令或真机步骤，以及为什么该 skip 不证明对应能力。

## 9. 工作树、提交和子智能体约束

- 禁止 `git add .` 和 `git add -A`；
- 禁止 `git reset --hard`、全量 checkout 或清理无关未跟踪文件；
- 只能显式暂存当前任务文件；
- 每次提交后重新确认用户既有四个暂存文档仍保持暂存；
- APK、反编译目录、设备截图和日志只有在计划明确列为证据产物时才允许纳入版本控制；
- 每个根因簇、Task 6–15 的重验或修复、Task 16 的发布证据分别提交；
- 子智能体只有在用户授权时才能创建；任何后续子智能体模型不得高于 `gpt-5.6-luna`；
- 子智能体报告不能直接作为完成证明，主智能体必须检查 diff 并重新运行验证。

## 10. 发布完成定义

以下条件必须同时满足：

- `test_workshop_patch.py` 零失败、零错误；
- 完整 discover 零失败、零错误；
- 每个 skip 都有明确外部条件，且不存在被 skip 的强制发布项；
- scanner、quality、coverage 和 performance 专项测试通过；
- helper DEX 构建成功并包含计划要求的类；
- APK 构建、资产一致性、zipalign、V2 和 V3 签名通过；
- 单 APK 真机链路通过；
- Split APK 在适用真实样本上真机链路通过；
- selectable 激活模式通过并能切回原文；
- always-on 激活模式通过且完成页文案准确；
- 真实样本 `missing == 0`，或用户明确选择“不完整测试补丁”且 UI 持续显示警告；
- 最终字体缺字集合为空，否则构建或发布被阻止；
- 新游戏、旧存档、rollback、跳转和语言切换均有证据；
- Task 13、14、15 分别拥有独立发布证据；
- 兼容性矩阵、发布清单、进度台账与实际产物一致；
- 没有任何 `FAIL`，所有强制要求均为 `PASS`。

真实设备或真实游戏条件缺失时，可以完成全部本地实现和自动化修复，但总体状态只能是“等待外部验收”，不能标记为全部完成。

## 11. 设计验收标准

后续实施计划必须：

- 从 Phase 0 开始，不预设 Task 6–15 已完成；
- 为 `test_workshop_patch.py` 的每个失败建立根因分类和可执行验证；
- 覆盖原计划 Task 6–16 的全部 Step 和门禁；
- 每个任务包含精确文件、接口、失败测试、运行命令、预期结果和提交边界；
- 明确区分 fixture、机器构建、真实游戏和真机证据；
- 不允许用宽松断言、删除测试或伪造 `missing == 0` 获得绿色结果；
- 将子智能体模型上限 `gpt-5.6-luna` 和脏工作树保护写入全局约束；
- 只有在发布完成定义全部满足时才允许将目标标记为完成。
